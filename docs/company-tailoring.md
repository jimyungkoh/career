# 회사별 이력서·포트폴리오 작성 규칙

회사별 맞춤 이력서와 포트폴리오를 작성·수정할 때 적용한다. 경력 사실의 원천은 `content/resume.md`와 `content/work-experience.md`이며, 회사별 산출물이 원문을 대체하지 않는다.

## 변하지 말아야 할 항목

### 기술 섹션 형식

- **회사별 이력서와 포트폴리오의 기술 섹션은 SSoT 이력서의 형식을 유지한다. 기술명을 백틱으로 감싸 나열하며, 맞춤 과정에서 임의 분류 라벨·카테고리·접두어를 추가하지 않는다.**
- `백엔드·데이터:`, `운영·비동기 처리:`, `화면·AI 응용:`, `주요 기술:` 같은 분류를 기술명 앞에 붙이지 않는다. HTML·PDF의 기술 칩에도 해당 라벨을 넣지 않는다.
- 형식 수정만 요청받았을 때는 기존 기술명·나열 순서·경력 내용을 바꾸지 않는다. 기술을 추가·삭제·재정렬하는 내용 변경은 별도 요청과 원문 근거를 확인한 뒤 수행한다.
- Markdown은 다음처럼 작성한다. 아래는 형식 예시이며, 모든 회사별 문서의 기술 목록을 이 예시로 일괄 교체하라는 뜻이 아니다.

```markdown
## 기술

`TypeScript` `NestJS` `Next.js` `MySQL` `Redis`
```

- HTML은 기존 `.chips` 안에 기술명만 `span`으로 배치한다. 라벨용 칩·굵은 분류 제목·새 기술 그룹을 생성하지 않는다.
- 활성·조건부·지원 보류·제외 등 지원 판단과 관계없이 같은 형식 규칙을 적용한다. 제외 문서의 형식 수정을 지원 재개로 해석하지 않는다.
- 사용자가 명시적으로 이 형식 변경을 요청하지 않는 한, 회사별 요구에 맞춘다는 이유로 위 규칙을 바꾸지 않는다.

### 원문 사실과 수치

회사·직책·재직/프로젝트 기간·담당 범위·기술 경험·성과 수치와 측정 조건은 원문 근거를 유지한다. 공고의 요구 기술을 후보자의 경험으로 바꾸거나, LLM 기반 고객사 평가를 LLM 응답 품질 평가 체계 경험으로 확대하지 않는다.

## 수정·생성·검증

1. 현재 diff와 기존 산출물을 확인하고 사용자 변경을 보존한다.
2. 기술 형식만 고칠 때는 기술 섹션 외 본문을 유지하고, 수정 전후 기술명과 순서가 같은지 확인한다.
3. 기존 HTML·PDF가 있는 회사별 문서는 Markdown 수정 후 같은 생성 절차로 재생성한다. 제외 문서에 파생물이 없으면 형식 수정을 이유로 새 제출용 파생물을 만들 필요는 없다.
4. [HTML 문서 규격](html-spec.md)과 [PDF 문서 규격](pdf-spec.md)에 따라 내용 일치·라벨 잔존·텍스트 추출 순서·링크·쪽수·잘림·한글 표시·페이지 밀도를 검증한다.
5. 형식 수정으로 밀도 기준을 벗어나더라도 경력 문장을 덧붙이거나 간격·종이 여백을 늘려 채우지 않는다. 측정값과 제한을 결과에 기록한다.
